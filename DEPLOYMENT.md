# Aawash — Deployment, Operations & Disaster Recovery Runbook

_Part 9 — Enterprise Deployment & Infrastructure. This document is
operational; no business logic lives here._

## 1. Environments

| Env         | Purpose                    | URL pattern                                       | Backend                            |
| ----------- | -------------------------- | ------------------------------------------------- | ---------------------------------- |
| Development | Local iteration            | `http://localhost:8080`                           | Shared Lovable Cloud dev project   |
| Preview     | Per-branch preview build   | `project--{id}-dev.lovable.app`                   | Same Lovable Cloud dev project     |
| Production  | Live customer traffic      | Custom domain + `project--{id}.lovable.app`       | Lovable Cloud production project   |

Secrets are isolated per environment via Lovable Cloud → Backend → Secrets.
No secret is ever committed to git. The client bundle only sees
`VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY`.

## 2. Required Secrets

Runtime secrets (managed in the backend, injected as `process.env.*`):

| Name                          | Purpose                                        | Rotation |
| ----------------------------- | ---------------------------------------------- | -------- |
| `SUPABASE_URL`                | Backend API URL                                | Managed  |
| `SUPABASE_PUBLISHABLE_KEY`    | Anon key (server + client)                     | Managed  |
| `SUPABASE_SERVICE_ROLE_KEY`   | Admin/service role — bypasses RLS              | Managed  |
| `SYSTEM_MAINTENANCE_SECRET`   | Shared secret for the cron webhook             | 90 days  |

Validation happens on every hit to `/api/public/health` via
`src/lib/env-validation.ts`. Missing or malformed values produce a
`503 degraded` response with the offending variable name.

## 3. Deployment

### Standard release

1. Merge to main. Lovable's build pipeline runs:
   - Type-check (`tsgo`)
   - Vite production build
   - TanStack route-tree generation
2. Click **Publish** in the editor (or approve via `preview_ui--publish`).
3. Watch `/api/public/health` return `200 ok` within ~60s.

### Rollback

- **Application:** Use *Version history* in the editor to restore an earlier
  commit, then re-publish.
- **Database:** Migrations are forward-only and idempotent (each is wrapped
  in a single transaction by Supabase). To reverse a schema change, author a
  new migration that undoes it — do not attempt manual `DROP` on production.
- **Assets/CMS content:** Both `assets` and `cms_pages` retain full version
  history; use `asset_rollback(id, version_id)` and `cms_rollback_page(...)`.

## 4. Health & Monitoring

### Public health endpoint

`GET /api/public/health` returns machine-readable JSON:

```json
{
  "status": "ok" | "degraded" | "down",
  "checks": {
    "app":      { "ok": true },
    "env":      { "ok": true },
    "database": { "ok": true, "latency_ms": 24 },
    "storage":  { "ok": true, "latency_ms": 31 },
    "auth":     { "ok": true, "latency_ms": 18 }
  },
  "env_checks": [{ "name": "SUPABASE_URL", "present": true, "valid": true }, ...],
  "duration_ms": 82,
  "ts": "2026-07-22T19:50:00.000Z"
}
```

Wire this into any uptime monitor (UptimeRobot, BetterStack, Pingdom).
HTTP 200 = healthy; 503 = alert.

### Admin dashboards

- `/admin/system` — live KPIs, integrity checks, maintenance toggle.
- `/admin/reports` — executive BI + CSV/PDF exports.
- `/admin/finance` — wallet ledger and revenue.

### Structured logs

Server code emits single-line JSON via `src/lib/logger.ts`. Categories:
`app`, `auth`, `security`, `finance`, `cms`, `media`, `api`, `audit`,
`performance`, `cron`. Correlate requests with `requestId` (generated by
`newRequestId()`).

## 5. Database Safety

- **Migrations** live in `supabase/migrations/`. Each file is atomic
  (single transaction) and idempotent where possible (`CREATE TABLE IF NOT
  EXISTS`, `CREATE POLICY IF NOT EXISTS`).
- **RLS** is enabled on every table in `public`. Explicit `GRANT` statements
  live in the same migration as the `CREATE TABLE`.
- **Integrity checks** run on-demand via `/admin/system` → *Run integrity
  checks*, and daily via the `system_run_maintenance` cron.

### Backups

Lovable Cloud (Supabase) provides automated daily point-in-time backups
retained for 7 days on the default plan. To trigger a manual backup or
export raw data:

1. Open **Backend → Advanced → Export data**.
2. Wait for the export bundle.
3. Store the encrypted bundle in your organisation's secure archive.

Restore is performed by Lovable support on request; recovery point ≤ 24h,
recovery time ≤ 4h.

## 6. Disaster Recovery Runbook

| Scenario                          | Action                                                       |
| --------------------------------- | ------------------------------------------------------------ |
| Health check returns `down`       | Check secrets in Backend → Secrets. Re-run health.           |
| Database unreachable              | Check Lovable Cloud status page. Enable maintenance mode.    |
| Accidental data deletion          | Restore from backup (contact Lovable support with timestamp). |
| Corrupted migration               | Author a compensating migration; never edit an applied one.  |
| Storage failure                   | Assets keep `asset_versions`; rebuild affected records.      |
| Region failure                    | Lovable failover is automatic; monitor `/api/public/health`. |
| Credential leak                   | Rotate `SUPABASE_SERVICE_ROLE_KEY` in the backend UI; rotate `SYSTEM_MAINTENANCE_SECRET` via the secrets tool. |
| Deployment failure                | Rollback via editor Version history; investigate build logs. |

### Enable maintenance mode

1. Sign in as Super Admin → `/admin/system`.
2. Toggle **Maintenance mode**, set a reason and ETA.
3. Public/authenticated users see the maintenance banner; Super Admins
   retain full access.
4. Toggle off when work is complete.

## 7. Security Posture (already applied)

- HTTPS enforced by Lovable Cloud CDN (Cloudflare).
- All `public.*` tables have RLS enabled with explicit policies.
- `SECURITY DEFINER` RPCs enforce authorization inside the function body.
- Customer child tables (`documents`, `notes`, `meetings`, `timeline`)
  gate on `can_access_customer()`.
- CMS drafts and asset folders are Super Admin only.
- Public webhook `/api/public/hooks/system-maintenance` requires **both**
  the Supabase `apikey` and `x-maintenance-secret` headers.
- No secrets are logged. `src/lib/env-validation.ts::redact()` is available
  for defensive log lines.

## 8. Performance Baseline

- Route-level code splitting is automatic (TanStack file routes).
- All list views use pagination and indexed lookups.
- Charts (`AnalyticsKit`) receive already-aggregated data from RPCs.
- Media served from private buckets via short-lived signed URLs.
- Long lists (members, sales, wallets) are query-scoped by role and time.

Load ceilings tested against the current tier:

| Workload                    | Ceiling (default tier)   |
| --------------------------- | ------------------------ |
| Concurrent logins           | ~200/min                 |
| Concurrent sale approvals   | Row-locked via `FOR UPDATE` in `approve_sale` |
| Wallet mutations            | Atomic RPCs, safe under contention |
| Report generation           | Client-side render/CSV; server aggregation only |

Scale up via Backend → Overview → Advanced settings → larger instance if
sustained load approaches these numbers.

## 9. Pre-deployment Checklist

Run before every production publish:

- [ ] `/api/public/health` returns `200 ok`
- [ ] `/admin/system` shows all integrity checks green
- [ ] No pending migrations in the editor
- [ ] Secrets present: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`,
      `SUPABASE_SERVICE_ROLE_KEY`, `SYSTEM_MAINTENANCE_SECRET`
- [ ] Latest security scan is clean or triaged
- [ ] Smoke-test: login → create customer → draft sale → approve sale →
      commission generated → wallet credited → withdrawal request (window
      permitting)
- [ ] Responsive check: mobile (≤430px), tablet (≥768px), desktop (≥1280px)
